# Handoff: Sheet -> fraterniti.one "Site BOQ" sync

Read this fully before touching code. Also read `plan.md` and the existing Site BOQ code first (see Step 0).

## 0. Mental model (what connects to what)

```
Google Sheet (TULSI rate sheet)  = the boss. Website only displays what the sheet had at the last sync.
        │
Apps Script (WebsiteSync.js, already written, lives inside the sheet)
        │   - every minute: GET /api/sheet-sync/pending   "did someone press the button?"
        │   - daily ~10 AM: runs a sync on its own
        │   - sheet menu:   runs a sync on demand
        ▼   sync = POST start -> POST chunk (one per category tab, 21 of them) -> POST finish
fraterniti.one API  (YOU build this)
        │   chunks go to a STAGING area tagged with runId.  Live data is untouched.
        │   finish = one DB transaction: replace live Site-BOQ data with the staged data.
        ▼   anything fails before finish => live data stays exactly as it was.
Site BOQ page  (already exists) + "Sync with sheet" button + "Last synced" label  (YOU add the button/label)
```

Cause and effect to keep in mind:
- Pressing the website button does NOT call the sheet. It only sets a "requested" flag in the DB. The sheet's every-minute poll sees the flag, then does the work. So expect 1 min pickup + ~1 min sync.
- Sheet edits never reach the website until a sync runs. That is by design (sheet is boss, website is read-only for this data).

## 2. Auth

- Env var `SHEET_SYNC_SECRET` (Vercel + local `.env`). Apps Script sends `Authorization: Bearer <secret>`.
- Compare with `crypto.timingSafeEqual`. Wrong/missing => 401, no detail. Never log the secret.
- These routes are only for the script; they must not use the user session. The admin button route (below) uses the normal admin session instead.
- Env var `SHEET_SYNC_ALERT_EMAIL` = who gets failure emails.

## 3. API the Apps Script already calls (do not change names/shapes without telling the human)

All JSON. Real example of every body: `sample-payload.json` (generated by running the real script on the 02-Nov backup).

| Route | Who | What it does |
|---|---|---|
| `GET  /api/sheet-sync/pending` | script, every minute | `{pending:boolean, requestId?:string, trigger?:'button'}`. `pending:true` only if a request exists, is not yet picked up, and no run is currently `running`. When it returns pending:true it marks the request `picked_up` so the next minute's poll does not start a second run. |
| `POST /api/sheet-sync/start` | script | body: `{requestId|null, trigger:'button'|'daily'|'menu', sheetName, sheetId, sites[], lockedSites[], tabCount}`. Create a `SyncRun` (status `running`, startedAt), return `{runId}`. If another run is `running` and younger than 10 min => 409. |
| `POST /api/sheet-sync/chunk` | script, once per tab | body: `{runId, tab:{category, tab, vendors[], items[]}}`. Store into staging keyed by (runId, category). **Idempotent**: the script retries on 5xx, so a repeated chunk for the same (runId, category) must replace, not duplicate. Reject unknown/non-running runId. |
| `POST /api/sheet-sync/finish` | script | body: `{runId, expected:{tabs, items, sites}}`. Check staged tabs/items == expected (else fail the run). Then, in ONE transaction, replace live data with staged data, set `lastSyncedAt`, run status `success`, delete staging for that run. |
| `POST /api/sheet-sync/fail` | script | body `{runId, message}`. Mark `failed`, delete staging, send the failure email. Live data untouched. |
| `POST /api/sheet-sync/request` | **admin button (session auth, admin role only)** | Creates a request (`requested`), returns 202 `{requestId}`. If one is already `requested`/`picked_up`/`running` => return that one, don't stack. |
| `GET  /api/sheet-sync/status` | Site BOQ page (session auth) | `{state:'idle'|'waiting_for_sheet'|'syncing'|'success'|'failed', lastSyncedAt, lastRun:{trigger,tabs,items,durationSec,error?}}` |

Body sizes: biggest chunk is ~63 KB (Kitchen Smallware), whole payload ~260 KB. No need for raising Vercel limits. Keep each route fast; the heavy work is the single transaction in `finish`.

## 4. Data shape (one item), from the real sheet

```json
{
  "itemKey": "Kitchen Smallware|asian wok imported|1",
  "row": 5, "sNo": 1, "name": "ASIAN WOK IMPORTED",
  "finalRate": 1155, "rateMissing": false, "finalVendor": "Gogia",
  "vendorRates": { "Gogia": 1155 },
  "notes": "",
  "sites": { "Ayodhya": { "qty": 2 }, "Mumbai": { "qty": 2, "remark": "...", "stage": "Ordered", "trackedAmount": 0, "boqLink": "...", "poLink": "...", "approvedVia": "...", "link": "...", "advGiven": 0, "followUp": "2026-11-10", "remarks": "..." } }
}
```

Rules that matter:
- `sites` contains only sites with at least one non-empty field. Missing key = nothing entered for that site.
- `itemKey` = `category|lowercased name|n-th occurrence`. Item names are NOT unique in the sheet (e.g. "Japanese Cocktail Glass" appears 3x, "Cream Siphon" in Kitchen and FOH). Never use name alone as a key. It is stable between syncs unless the sheet's row order of duplicates changes.
- `finalRate: 0` + `rateMissing: true` means "rate not found yet" in the sheet (the sheet shows 0.00). Show "Rate pending", never "₹0". 189 of 680 items are like this today.
- Vendors named `automation` are real columns (BOQ-import rates), not junk. Show them, don't filter.
- **Compute amounts on the website: qty × finalRate.** Do not expect sheet totals. (The sheet's own "Total Qty / Total Cost" formulas are missing for Furniture rows 67–109, so the sheet understates Furniture by about ₹6.76 lakh; the website will be right and will differ from the sheet's Dashboard there. That is expected, mention it in the UI tooltip or release note, not an error.)
- `trackedAmount` is the sheet's per-site tracking "Amount" column. It is not qty × rate. Keep it separate; label it clearly.
- Photos are NOT in the payload (v1). If the website already stores item photos, a sync must not delete them. Match photos to items by `itemKey`, and keep orphaned photos rather than dropping them.
- `lockedSites` = sites whose order is delivered/locked in the sheet. Store a `locked` flag per site; show a lock badge. Data for them still arrives normally.

## 5. Sites

- `start.sites[]` = the sheet's Sites tab: `{position, name, shortCode?, note?, openingDate?}` (17 today).
- Match to website sites by normalised name (trim, collapse spaces, case-insensitive). No match => create the site.
- A site that was previously created from the sheet but is no longer in `sites[]` => mark **archived** (do not delete). If the human wants delete instead, they'll say so.
- Never touch sites that were created by other parts of the app and never came from the sheet, unless they match by name.

## 6. Button + status UI (Site BOQ page, admin only)

States and exact wording (keep it plain):
- `idle`: button "Sync with sheet" + small text "Last synced: 3 Nov, 10:07 AM (by button)".
- after click: "Waiting for the sheet… (up to a minute)" -> "Syncing… (1–2 min)" -> "Done — 680 items, 17 sites".
- If a request is not picked up within 3 minutes: show "Sheet did not respond. Its auto-trigger may be off — ask Abhishek." and send the alert email once.
- `failed`: show the error text from the run and keep showing the previous lastSyncedAt (data is still the old one).
- Poll `/status` every 3–5 s only while a request/run is active; stop otherwise.
- Reaper: any run `running` for more than 10 min => mark `failed` ("timed out"), delete its staging, send alert email. Do it lazily inside `/status` and `/pending` (no cron needed on Vercel).

## 7. Failure email

Use the app's existing mail function. To `SHEET_SYNC_ALERT_EMAIL`. Subject: `Fraterniti One – sheet sync failed`. Body: trigger, time (IST), error message, last successful sync time. Send once per failed run.

## 8. Daily 10 AM

Handled entirely by the Apps Script trigger (it runs between 10:00 and 10:15 IST). The website needs no cron. Do not add one.

## 9. What to test (use `sample-payload.json`)

1. Happy path: start -> 21 chunks -> finish. Check item/site counts equal `finish.expected`; page shows the new data and a new lastSyncedAt.
2. Atomic: send start + 10 chunks, then `/fail`. Live data identical to before.
3. Atomic: send chunks then finish with a wrong `expected.items`. Run fails, live data unchanged.
4. Idempotent: send the same chunk twice. No duplicate items.
5. Auth: no/incorrect secret => 401 on every script route; admin routes reject non-admin.
6. Stacking: click the button 5 times quickly => exactly one request/run.
7. Re-sync with a site removed from `sites[]` => that site archived, not deleted; its old data hidden from active views.
8. Duplicate-name items (Japanese Cocktail Glass) stay as separate rows after sync.
9. `rateMissing` items render "Rate pending".

## 10. Do NOT

- Do not create a second copy of Site BOQ tables if the existing ones fit.
- Do not change the Apps Script contract above silently; if you must, say exactly what and why so the script can be changed too.
